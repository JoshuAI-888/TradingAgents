# Capture definition compatibility migration

Observed in the actual browser on 3 October 2026: entering Price ≤10 through Add filter produces `{field:"price",min:null,max:10,_label:"Price"}`. The fixture's exact definition `{field:"price",max:10}` has two captures, but the UI-created form reports no baseline. Removing the presentation-only fields through the supported deep link retrieves the captures. This is a confirmed history-discovery gap, not missing capture data.

The current `_snapshot_key` hashes the entire raw `ScreenDefinition` plus version and original preset metadata. Private schedules separately pin a hash of their raw immutable screen/preset envelope. A direct normalization change would abandon old keys or schedule lookups. Do not overwrite captured definitions, criterion observations, stored hashes or note identities.

## Build sequence and acceptance checklist

1. Add a versioned semantic definition function that removes only `_label` and null `min`/`max`. Preserve filter order, repeated slots/windows, bounds including zero, exclusivity, currency, source, market, ETF/watchlist settings, preset identity and all other keys. Reject invalid field/bound shapes; do not silently erase unknown semantic fields. Record current 22 preset definitions/hashes as preservation evidence.
2. Add a private, owner-scoped mapping from semantic definition identity to original history keys/schedule hashes. Backfill from each stored immutable definition; retain the raw original as the authoritative evidence. Legacy records without a provable definition cannot be merged heuristically. Keep deployment-shared manual history separate from authenticated-owner schedule history. Add indexes and bounded paging; no broad client-directed cross-owner lookup.
3. Discover compatible capture histories through the mapping while preserving exact capture IDs and chronology. Merge metadata pages deterministically across proven aliases without duplicating captures. Mixed versions/incomplete evidence retain existing rejection behavior. Bridge raw criteria to normalized criteria only when each corresponding original slot proves semantic equivalence; never renumber repeated criteria.
4. Retain existing scheduled definition/hash/revision/CAS publication contracts. New UI-created requests can discover the original owner-private schedule through the mapping; edits/publications still use its exact pinned envelope. Preserve pair review notes and selection identities; map discovery must not alter capture pair scope.
5. Verify UI creation → capture → reload → minimal deep link → Changes → criterion sorting → private review/export. Test both directions (old labelled to new minimal and old minimal to UI-labelled), repeated 30/60-day bounds, zero/negative/exclusive thresholds, actual mismatches, pagination over aliases, two owners/account switch, concurrent backfill/new capture, and rollback. Reconcile downloaded membership and note identities against original records.
6. Introduce this additively with a disabled cutover switch; measure indexed real PostgREST latency and query limits. Enable only after backfill coverage and Auth isolation qualify. Rollback restores the original raw-key discovery without deleting mapped or captured data.

This migration is required before calling equivalent-filter history continuity complete under R04/R06/R10. It remains unbuilt. It is not permission to broaden ownership or merge histories based on labels, stock names or approximate bounds.
